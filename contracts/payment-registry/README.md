# NODUS Payment Registry (scaffold)

This crate is an isolated NEAR contract foundation. It is **not** a production-ready contract and does not independently verify EVM transactions. NODUS's backend remains the trusted verifier for Base/Arbitrum transaction receipts, CCTP/IRIS evidence, recipient and amount, and chain finality before it submits an attestation.

## Existing NODUS rules reflected here

- Invoice IDs and payment attempt IDs are UUIDs generated by PostgreSQL `gen_random_uuid()`. The registry accepts only canonical lowercase UUID text (`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`).
- Invoice amounts are positive `bigint` values in currency minor units. Invoice currency is an uppercase three-letter code; the current live CCTP route specifically accepts USD and USDC.
- A draft invoice can be opened; open and overdue invoices can be paid. Paid and cancelled invoices cannot be edited. Amount, currency, or business ownership cannot change while a live attempt is active or a settlement exists. Paid status requires the verified reconciliation path.
- A live attempt has a UUID idempotency key and is unique per invoice while active. There can be one settlement per attempt. Verified partial settlements are accumulated across attempts; the invoice becomes paid once the cumulative value equals the invoice amount. An overpayment is recorded for review rather than marking the invoice paid.
- The current live route is Base Sepolia to Arbitrum Sepolia, uses USD/USDC with six token decimals, and binds the merchant recipient from the business profile. The registry stores only the invoice UUID and payment terms; it does not store customer name, email, invoice description, share token, quote, or raw evidence.

The above is based on `src/app/actions/invoices.ts`, `src/app/api/pay/[token]/attempt/route.ts`, and the invoice, attempt, and reconciliation migrations. The contract intentionally covers successful settlement records and partial/full/overpaid outcomes only. Failure, refund, incomplete deposit, expiry, and manual-review lifecycle attestations remain future work and must be specified against the database state machine before being added.

## Frozen V1 data encoding

- **Invoice and attempt IDs:** canonical lowercase UUID text, 36 ASCII bytes, hyphens at offsets 8, 13, 18, 23, with all other characters lowercase hexadecimal. Contract commitment encoding uses the 16 raw UUID bytes.
- **Settlement/reconciliation IDs:** same UUID encoding as the database settlement ID (`payment_settlements.id`) and attempt ID.
- **Amounts:** unsigned 128-bit integers. JSON wire values use NEAR's `U128` decimal-string representation; no floating point. Invoice `amount_minor` is currency minor units. For USD, one minor unit is one cent. Token `amount_base_units` uses the token's base units. Conversion follows NODUS reconciliation: `minor = base_units * 100 / 10^decimals`; therefore the target token amount is `amount_minor * 10^(decimals - 2)`. Division must be exact for a settlement to be representable in USD minor units. V1 rejects decimals below two and checks arithmetic overflow.
- **EVM chain IDs:** positive `u64` integer values, transported as JSON integers and encoded big-endian in the terms commitment. V1 pins the current NODUS route to Base Sepolia `84532` and Arbitrum Sepolia `421614`.
- **EVM token and recipient addresses:** exactly 20 bytes, represented at the API boundary as `0x` followed by 40 lowercase hexadecimal characters. Mixed-case inputs must be normalized by the backend before submission; the contract rejects noncanonical forms to avoid replay-key aliases.
- **EVM transaction hashes:** exactly 32 bytes, represented as `0x` plus 64 lowercase hexadecimal characters. Source and destination uniqueness keys are `(chain_id, normalized_hash)`.
- **Terms commitment:** SHA-256 over the following byte sequence, with no JSON serialization: ASCII `NODUS_PAYMENT_TERMS_V1\0`; 16 raw invoice UUID bytes; `amount_minor` as 16-byte unsigned big-endian; destination chain ID as 8-byte unsigned big-endian; token decimals as one byte; 20 raw token-address bytes; 20 raw merchant-recipient bytes; currency byte length as 2-byte unsigned big-endian; currency UTF-8 bytes. The stored commitment is lowercase `0x` + 64 hex characters. The contract computes it from the registered terms; it does not trust a caller-supplied digest.
- **Evidence digest:** SHA-256 over this exact no-JSON sequence: ASCII `NODUS_CCTP_SETTLEMENT_EVIDENCE_V1\0`; raw 16-byte invoice UUID; reconciliation UUID; attempt UUID; source chain ID as 8-byte unsigned big-endian; source transaction hash as 32 raw bytes; source block number as 8-byte unsigned big-endian; source block hash as 32 raw bytes; CCTP message nonce as 8-byte unsigned big-endian; CCTP message hash as 32 raw bytes; destination chain ID as 8-byte unsigned big-endian; destination transaction hash as 32 raw bytes; destination block number as 8-byte unsigned big-endian; destination block hash as 32 raw bytes; token address as 20 raw bytes; merchant recipient as 20 raw bytes; received amount as 16-byte unsigned big-endian; token decimals as one byte; verifier policy version as 4-byte unsigned big-endian. The contract recomputes this digest from the attestation fields and rejects a mismatch. This commits to the backend's verification summary; it does not make the contract an EVM verifier. Raw evidence and PII stay off-chain.

## Methods in the scaffold

| Method | Authorization | Effect |
| --- | --- | --- |
| `new(owner_id, registrar_id, initial_attestor)` | one-time initialization | Sets separate owner/registrar roles and initial attestor. |
| `register_invoice(invoice_id, terms)` | registrar or owner | Validates supported terms, computes the terms commitment, and creates an open invoice once. |
| `register_attempt(attempt_id, invoice_id, source_chain_id)` | registrar or owner | Creates a unique attempt linked to an open invoice and its source chain. |
| `attest_settlement(input)` | current attestor | Validates chain, token, recipient, decimals, positive amount, UUIDs, hashes, replay keys, and invoice terms; records one settlement per attempt; accumulates partial value; marks an exact cumulative payment paid; marks overpayment as review-required. |
| `add_attestor(account_id)` / `remove_attestor(account_id)` | owner | Supports overlap rotation: add and verify a new attestor before removing the old one. The owner cannot remove itself through this method. |
| `get_invoice`, `get_attempt`, `get_settlement`, `is_attestor` | public views | Returns registry state without exposing private invoice fields. |

The initial transition model is `Invoice Open -> Paid` on exact cumulative value, or `Invoice Open -> ReviewRequired` on overpayment. A registered attempt becomes `SettlementRecorded` once. Each attestation outcome is `Partial`, `Verified`, or `Overpaid`. A partial settlement leaves the invoice open so a later registered attempt can complete it. A review-required invoice cannot accept another attempt, matching the database's active unresolved overpayment behavior. These on-chain records mirror only the verified settlement subset of NODUS's richer lifecycle; they are not the canonical UI status source.

## Backend delivery and retry design

1. The existing backend independently verifies EVM source and destination transactions, the Circle message binding, exact merchant transfer, amount, and finality.
2. In the same PostgreSQL transaction that records the successful `payment_settlements` reconciliation, the future integration should insert one pending outbox row keyed uniquely by the reconciliation ID. Store only the UUIDs, canonical attestation payload, digest, delivery state, retry metadata, and NEAR transaction reference. Do not store PII in the outbox payload.
3. A worker claims rows with a database lock/lease (for example `FOR UPDATE SKIP LOCKED`) and submits `attest_settlement` to NEAR using the authorized backend attestor account.
4. The worker records transaction hash and execution outcome. It marks delivery complete only after confirming the contract's settlement view for that reconciliation ID.
5. On timeout or lost response, the worker queries `get_settlement(reconciliation_id)` first. If present with the expected fields, mark delivered. If absent, retry the same reconciliation ID and same canonical payload. Contract uniqueness on reconciliation ID, attempt ID, and `(chain_id, transaction_hash)` prevents a second record. A mismatch becomes manual review, never a new settlement ID.

The PostgreSQL commit and NEAR transaction are **not atomic**. The outbox makes delivery recoverable and idempotent; it does not create a distributed transaction. The database remains the application source of truth, while NEAR is an attested audit mirror.

## Trust and security boundary

The backend attestor is trusted to submit accurate terms and reconciliation evidence only after independent EVM verification. NEAR authenticates the NEAR account that called the contract; the contract cannot infer that an external EVM transaction happened. A compromised attestor can lie within the authority it has. Protect the key, restrict it to the delivery worker, rotate with overlapping authorization, and separately govern owner/registrar keys. This scaffold has no multisig, upgrade control, canonical Circle allowlist, signature verification of IRIS, EVM light client, expiry/finality proofs, gas/storage limits, or full DB lifecycle parity. Those are explicit pre-deployment decisions.

## Development

```powershell
cargo test --locked --manifest-path contracts/payment-registry/Cargo.toml
cargo near build non-reproducible-wasm --manifest-path contracts/payment-registry/Cargo.toml
cargo near abi --manifest-path contracts/payment-registry/Cargo.toml
```

The contract pins `near-sdk` exactly and commits a `Cargo.lock`. `cargo-near` is a developer tool and is installed separately. Unit tests use NEAR's mocked runtime; they are not sandbox or testnet integration tests. NEAR Workspaces Rust documents sandbox test support for macOS and Linux, not Windows. Run integration tests in Ubuntu CI (build the WASM, launch the supported sandbox test runner, deploy locally, and exercise JSON methods and replay/state behavior). A TestNet integration test is a later, explicitly authorized activity and is not part of this bootstrap.
